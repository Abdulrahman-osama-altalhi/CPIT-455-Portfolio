Week 01–02 Class 01 · Domain Spine

Dependable Systems

5 Attributes (Availability, Reliability, Safety, Security, Resilience) · Sources of Failure · Achievement Strategies
My evidence: mapping dependability to our team's project

I selected my team's MedAlert system as the target, a clinic medication management application where dependability is not a luxury but a clinical requirement. I worked through each attribute and mapped it to a concrete failure mode the system must prevent.

AttributeWhat it means in MedAlertWhy it matters
AvailabilityThe system must be reachable across all shifts, day, night, emergency.Medications follow fixed schedules. A nurse cannot wait for a restart at 3 AM.
ReliabilityEvery dose record is accurate; no silent failure, no duplicate logging.A wrong record is as dangerous as a wrong dose, it leads to double-administration.
SafetyThe system never permits an overdose, never silently drops an alert.A missed alert can become a missed dose. The consequence is patient harm.
SecurityPatient records protected via Firebase Authentication, role isolation, and admin 2FA.Exposure of medication history could enable targeted harm against a patient.
ResilienceThe system degrades gracefully, when the DB is unreachable, the API returns 503 and halts dose logging instead of silently failing.Silent failure is the worst outcome. An honest failure is recoverable; a hidden one is not.
Key insight from class. The attributes are not independent. A security breach often forces the system offline, which destroys availability, which causes reliability failures (missed alerts), which becomes a safety event. One attack, all five attributes degraded.
Sources of failure I identified
  • Hardware: Vercel/Supabase region outage, clinic network drop, tablet malfunction.
  • Software: Bugs in the cron-based alert scheduler, race conditions in concurrent dose logging, database connection pool exhaustion.
  • Operational (most likely): Nurses confirming doses without verification, admins misconfiguring schedules. As the lecture stated, most "system" failures are actually operational failures.
Proposed dependability strategy
  • Prevention. Strict input validation on dose entries; role-based access control limits who can modify schedules.
  • Verification & Validation. Backend rejects any actual_dosage > max_dose, caught at the boundary before it can become a dose event.
  • Fault Tolerance. 503 response with halted dose logging when DB is unreachable. No silent failures.
  • Redundancy. Two independent notification channels, FCM push and SendGrid email, so a single channel failure cannot drop an alert.

Week 03–04 Class 02 · Chapter 10

Reliability Engineering

Fault → Error → Failure Chain · POFOD / ROCOF / AVAIL · 8 Commandments of Reliable Programming
System profile

MedAlert serves clinical staff, nurses, doctors, admins. Medication events are predictable and structured (3–6 events per patient per day), not random consumer traffic. Peak load is concentrated at morning rounds and shift handover. Demand is not random, it is time-critical.

My metric selection: why POFOD over ROCOF
MetricDefinitionMy verdict
POFODProbability of Failure on Demand, success rate per discrete request.Primary. Every alert and every dose-log is a discrete demand. Each one must succeed.
AVAILProportion of time the system is operational.Secondary. Must stay up during shift hours.
ROCOFRate of failure occurrences per time unit.Less useful, MedAlert's risk is per-demand, not time-density.
My reasoning. The question for a safety-critical system with intermittent demand is not "how often does it fail per hour" but "did it succeed THIS time, for THIS patient, at THIS dose?" That is exactly the question POFOD answers.
The Fault → Error → Failure chain: applied to MedAlert

I traced one concrete bug class through the full chain, a real risk in our cron-based scheduler.

Fault → Error → Failure
Fault
Static defect
Cron scheduler reads timestamps without timezone normalization. Lies dormant in code.
→
Error
Wrong internal state
After DST change, the grace-window check is off by one hour; doses appear "not yet due."
→
Failure
Visible to user
Missed-dose alerts are not fired. Nurse not notified. Patient may miss medication.
My proposed reliability strategy for MedAlert

The cron-based alert engine is the highest-risk component. My recommendation: store all schedule timestamps in UTC, use ALERT_GRACE_MINUTES as an environment variable (not magic number), and pair the cron with a heartbeat log, if the cron skips a cycle, the next cycle catches up.

Commandments applied in MedAlert
  • Validate all inputs. Backend rejects actual_dosage > medication.max_dose, implemented as a hard constraint at the API layer.
  • Handle all exceptions. All exceptions caught, logged, and surfaced as structured JSON errors. No silent failures.
  • Include timeouts. External calls to FCM and SendGrid have timeouts; failure cascades to the secondary channel.
  • Name all constants. ALERT_GRACE_MINUTES is configurable via env, not hardcoded. No magic numbers in safety-critical paths.

Week 05–06 Class 03 · Chapter 12

Safety Engineering

Hazard → Accident → Damage · ALARP Triangle · Fault Tree Analysis · "Shall Not" Requirements · Safety Case
The hazard chain: my worked example

I traced one critical scenario through the full hazard chain. The point was not just to identify a risk, but to design the intervention that breaks the chain, which the team then implemented at the dose-confirmation endpoint.

Hazard → Accident → Damage (with intervention)
Hazard

A nurse attempts to administer a dosage that exceeds the safe maximum (typo, rushed input, or wrong medication selected).

Accident

If accepted, an excessive dose enters the dose log, and clinically, into the patient.

Damage

Patient harm, toxicity, overdose, hospitalization, or worse. Hospital faces clinical and legal liability.

Intervention

The backend rejects any submission where actual_dosage > medication.max_dose. The control is at the API, not the UI, cannot be bypassed.

The ALARP Triangle, applied to MedAlert
ALARP, As Low As Reasonably Practicable
Intolerable Overdose via dose-log submission. Designed out, backend hard-blocks any value exceeding max_dose. No nurse, no admin can override.
ALARP Third-party (FCM / SendGrid) temporary outage. Cannot guarantee 100% uptime of an external service. Reduced via dual-channel redundancy, push and email are independent.
Acceptable A <1-minute delay between scheduled time and alert delivery (cron runs every minute + grace window). Negligible to patient safety; tolerated by clinical protocol.
My Fault Tree, top event: "Patient Administered Wrong Dose"
Fault Tree Analysis
Design insight. The Fault Tree forced the team to think one level deeper than "validate input." Each branch demands its own control. The OR gate means we cannot prevent only the most likely branch, we have to defend all three.
"Shall Not" safety requirements I specified for the team
  • SR1. The system shall not accept a dose submission where actual_dosage > medication.max_dose.
  • SR2. The system shall not silently fail. If PostgreSQL is unreachable, the API shall return 503 and halt dose logging.
  • SR3. The system shall not allow a nurse role to delete medications or modify dose schedules, only doctors and admins may do so.
  • SR4. The system shall not permit medication deletion without a double-confirmation token, preventing accidental data loss.
My individual work in V1. I specified all four "Shall Not" requirements above based on hazard analysis. The team translated them into backend constraints (the max_dose check, the 503 fail-safe, the role middleware, and the double-confirmation token logic). I also presented the Fault Tree analysis in the V1 deck.

Security Engineering

CIA Triad · Safety vs Security · Risk Vocabulary · Misuse Cases · 10 Design Guidelines · Security Assurance Case
The CIA Triad, applied to MedAlert
DimensionConcrete threatControl in MedAlert
ConfidentialityA nurse from one ward viewing another ward's patient medication history.Strict role isolation enforced by middleware. A nurse cannot access doctor views and vice versa. JWT signed with a ≥32-character secret.
IntegrityA malicious insider modifying a schedule to administer a harmful drug.Only admins have full CRUD; doctors are read-only on medication history; nurses can only mark doses administered. All actions logged to alert_logs via the audit service.
AvailabilityA DoS attack or accidental traffic spike taking down the system.Rate-limit middleware on all endpoints. Read-only fail-state when DB unreachable (503 instead of silent corruption).
Safety vs Security: the distinction I learned
Safety protects users from accidental harm, bugs, race conditions, human error. The adversary is nature and complexity. Security protects users from intelligent, adaptive adversaries, insiders, hackers, social engineers. The adversary thinks, adapts, and attacks your defenses. Different mindset, different controls.
Misuse case: credential theft
Misuse Case, Stolen Credentials Attack
Security Assurance Case I drafted for the team
  • System description. Three-tier web application: React 18 client → Node.js + Express API → PostgreSQL 15 (hosted on Supabase). Auth via Firebase, notifications via FCM + SendGrid.
  • Threat analysis. Primary adversaries: insider misuse by clinical staff, external credential theft, API injection. Each modeled as a distinct misuse case.
  • Design rationale. Defense in depth, platform-level (Firebase Auth, JWT), application-level (role middleware, rate-limit middleware), data-level (audit service, daily backup, double-confirmation tokens).
  • V&V evidence. Admin 2FA via TOTP at login. All exceptions logged as structured JSON. Daily pg_dump backup at 02:00 server time. Role isolation enforced at API layer, not just UI.
Three design guidelines applied in MedAlert
  • Defense in Depth. Firebase Auth (platform) + role middleware (application) + audit log + admin 2FA, three layers, four controls. Never one point of failure.
  • Fail Securely. If the database is unreachable, the API returns 503 and halts dose logging. The default state on failure is locked, not open.
  • Log User Actions. Every alert and every dose event is logged to alert_logs via the audit service. No role can delete this log.
My individual work in V1. I drafted the security assurance case structure and the three design-guideline narratives above. I also presented the security threat model in the V1 deck, including the misuse case for credential theft and how role isolation defeats it.

Week 09–10 Class 06 · Chapter 14

Resilience Engineering

Cybersecurity · Sociotechnical Resilience · Swiss Cheese Model · R&R Strategies · Human-in-the-Loop
From reliable to resilient: my reframing for the team

Reliability is about delivering service when everything works. Resilience is about delivering critical service when components fail. For MedAlert, I argued the critical service is one sentence: a nurse can always know what the patient was supposed to receive, even when the DB is down, the cron is delayed, or FCM is throttled.

The failure chain: applied to a real risk in our system
Fault → Error → Failure
Fault
Connection leak
DB connection pool leaks connections under load; eventually exhausted.
→
Error
Failed queries
The cron-based alert checker cannot query dose_schedules; alert detection halts.
→
Failure
Round missed
No missed-dose alerts fire during a shift. Up to 40 patients miss automated reminders.
R&R strategy I documented for MedAlert
EventRecognitionResistance
API or scheduler crashPM2 process manager detects process exit immediately. Structured exception logs forwarded to admins.PM2 auto-restart. Until the process is back, the API returns 503, known failure, not silent.
Database unreachableConnection health check fails on first request after timeout.API returns 503; dose logging halts. No corrupted writes. Once DB recovers, normal operation resumes.
Push (FCM) channel downFCM call returns error or times out.SendGrid email alert is still independently dispatched. Two channels, one message.
Unauthorized access attemptRole middleware rejects request and writes to audit log. Admin alerted via dashboard.Firebase session invalidation. Admin enforces password reset and reviews audit trail.
The Swiss Cheese model: three defensive layers I mapped
Three Layers · Holes That Don't Line Up
1
Technical layer
  • Role middleware + Firebase Auth
  • Rate limiting on endpoints
  • max_dose validation at API
  • PM2 auto-restart on crash
  • Daily pg_dump backup
2
Human layer
  • Nurses confirm dose at administration
  • Doctors can verify medication history
  • Admins review audit logs
  • Double-confirmation for deletions
3
Organizational layer
  • Admin 2FA enforcement at login
  • Daily backup as recovery insurance
  • Audit trail for accountability
  • Clinical SOPs around manual fallback
The principle. Make the defenses different so the holes don't align. For an error to harm a patient, all three layers must fail simultaneously, and they're designed to fail differently.
The sociotechnical factor: when automation hits its limit

Automated resilience handles common failure modes. But when the API returns 503 (DB unreachable) during a medication round, the system escalates to humans, nurses revert to the printed medication administration record (the clinical paper protocol that pre-dated MedAlert). The admin is notified via the dashboard. The human is not a fallback of last resort; they are the final, irreplaceable layer of the Swiss Cheese model.

My individual work in V1. I mapped MedAlert's existing controls (which the developers had implemented) onto the Swiss Cheese model, showing how the technical, human, and organizational layers combine to prevent single-point failures. This made the team's existing design legible as a resilience strategy rather than a list of features.

Software Reuse

Reuse Landscape · Application Frameworks · Software Product Lines · The Ariane 5 Lesson
MedAlert's positioning: Development with Reuse

MedAlert is built with Development with Reuse. The team composed proven external components rather than build core infrastructure from scratch. The planning factors I documented:

  • Schedule. Semester-bounded delivery. Building auth from scratch adds weeks of risk and offers no clinical value.
  • Criticality. A safety-critical system needs battle-tested components, Firebase Auth has billions of deployments behind it; an in-house auth has zero.
  • Team skills. Strong Node.js and React competency. Framework alignment maximizes productivity.

CoreNode.js 20 + Express 4API backbone, generic routing and request handling.

The Ariane 5 lesson: what I took from it
The risk. Ariane 5 failed because a module validated for Ariane 4's velocity caused an overflow at Ariane 5's higher speed. The engineers assumed: "it worked before, it'll work again." That assumption killed the rocket.

How it applies to MedAlert. Firebase Auth is battle-tested for consumer apps, but MedAlert's role boundaries (nurse/doctor/admin), admin 2FA, and clinical session timeouts are not the typical consumer scenario. The team validated Firebase Auth specifically against our role middleware before integration. Reuse without re-validation is just a delayed bug.
Industry alignment: Microservices

MedAlert's reuse strategy positions it for microservices evolution. The notification layer (FCM + SendGrid) is decoupled from the core application. If a clinic later requires on-premise email instead of SendGrid, the team swaps one component without touching medication logic. Reuse and replaceability are two sides of the same coin.

The glue code problem
The mismatch. The alert service emits events as internal JavaScript objects. FCM requires its own message schema with device tokens; SendGrid requires a different schema with email payloads.

The solution. The notification service acts as the adapter, it transforms each alert event into both target formats and dispatches them in parallel. Parameter incompatibility resolved without modifying the alert service or the third-party APIs.
Validation and identified risk
  • Integration plan. Each service tested in isolation, then pair-tested with neighbors, then end-to-end via the deployed Vercel preview.
  • Risk I identified. Firebase Auth rate limits, if all nurse devices authenticate at shift start, the provider may throttle. Mitigation: stagger logins and use the 30-min JWT session window.

Distributed Software Engineering

Distributed Characteristics · Client-Server · Architectural Patterns · Middleware · SaaS · Scaling & Security
MedAlert's positioning: Multi-Tier Client-Server

MedAlert uses multi-tier client-server because it matches the requirements: structured data, role separation, centralized control, distributed access. One authoritative database (Supabase) and many client devices (nurse tablets, doctor workstations, admin terminals).

Why not peer-to-peer? MedAlert needs one authoritative source of truth for medication schedules. In a P2P model, two nurse devices could diverge on whether a dose was administered, a split-brain that causes either a missed dose or a double-dose. Centralized = consistent.
Node distribution
MedAlert Distributed Architecture
Client Tier
React 18 SPA · Vercel. Nurse tablets, doctor workstations, admin terminals. Service worker for FCM web push. No business logic, all enforcement is server-side.
↓ HTTPS · Axios

Node.js 20 + Express 4. Controllers, role middleware, rate-limit middleware, cron job (missed-dose checker every minute), audit service. PM2 process manager for reliability.
↓ Postgres protocol · TLS

PostgreSQL 15 on Supabase. Managed database with built-in replication and backup. schema.sql + migration files versioned in repo. Daily pg_dump for additional safety.
↓ HTTPS · external SaaS
External (SaaS)
Firebase Auth + FCM · SendGrid. Auth, push notifications, and email, consumed as SaaS. No infrastructure to maintain; provider handles scaling.
Failover plan
FailureResponse
API process crashPM2 auto-restart within seconds. Vercel-hosted frontend continues to render the last-cached state.
Supabase / DB unreachableAPI returns 503 and halts dose logging. This is by design, silent failure is the worst outcome. Once connectivity is restored, operation resumes.
FCM push channel downSendGrid email is independently dispatched. Two channels, one message, single channel failure cannot drop the alert.
Security in transit

All client–server traffic is encrypted with TLS (handled by Vercel/Supabase). JWT tokens are signed with a ≥32-character secret stored in JWT_SECRET. Admin login enforces TOTP-based 2FA, raising the bar for the highest-privilege role.

SaaS alignment

MedAlert leverages SaaS extensively, Firebase Auth, FCM, SendGrid, Supabase, Vercel. The team focuses on clinical logic, not infrastructure. The trade-off is dependency on external providers, mitigated by the dual-channel notification design and the daily backup.

Week 15–16 Class 10 · Chapter 20

Multi-Tier Architecture & Middleware

Tier Architecture Selection · Middleware Role · Validation & Localized Control · Microservices Alignment
MedAlert's choice: Thin Client, Multi-Tier

MedAlert uses a thin-client multi-tier architecture. The React SPA renders the UI and manages local state, but all business logic runs server-side. The reasoning:

  • Server-side enforcement. Safety rules (max_dose validation, role checks, double-confirmation) must execute on the server. Client-side validation can be bypassed by a determined user.
  • Consistent rules across devices. Logic on a server we control. A fat-client approach means many potential points of inconsistency per ward.
  • Device management. Thin clients are easy to replace. A broken tablet is replaced in under a minute, no local state to migrate.
Middleware role in MedAlert

Express middleware in MedAlert is exactly the textbook example, composable layers that bridge concerns:

  • Auth middleware. Verifies the Firebase JWT on every request. Without this, the request never reaches the controller.
  • Role middleware. Enforces nurse/doctor/admin boundaries. A nurse calling an admin endpoint is rejected here, before any business logic runs.
  • Rate-limit middleware. Protects against accidental traffic spikes and brute-force attempts.
  • Validation middleware. Schema validation on every input, including the actual_dosage ≤ max_dose safety check.
  • Error handler middleware. Catches every exception, logs it, and returns structured JSON instead of a stack trace.
Localized failure: preventing cascade collapse
If the database tier goes down. The application tier detects the failed connection check. It immediately returns 503 to the client and halts new dose logging. The UI shows an honest error. Critically, the system does not pretend to function, it states what it can and cannot do. This is the difference between failure (recoverable) and silent failure (catastrophic).
Industry alignment: Microservices evolution path

The current MedAlert application tier is a monolith, all logic in one Node.js process. But the modules (alert service, audit service, notification adapter) are designed as logically independent components. If a clinic scales to 1000+ beds, these modules can be extracted into independent microservices with their own deployment pipelines, scaling independently. The current design does not block this evolution, it enables it.

My individual work in V1. I documented the multi-tier rationale and the middleware chain on the V1 presentation deck. I framed why thin-client server-side enforcement is the right choice for a safety-critical system, and used the max_dose check as the canonical example of why client-side validation alone is insufficient.

Clinic Medication Management System · Healthcare · Web Application

H-Stack reflection

Authentic notes on what changed in how I think.

Market mindset

Every design decision can be defended in a business meeting. POFOD over ROCOF because clinics measure success per patient, not per hour. ALARP because infinite safety is infinitely expensive. Documentation is not overhead, it is the product.

Evidence-first

From "I know the stack" to "I can prove this stack is the right choice for a thin-client medication dashboard, given these three planning factors." Evidence is not extra work. It is the work.

Communication

Writing "Shall Not" requirements taught me to communicate with engineers and regulators simultaneously. The team built max_dose validation; my job was to explain why this is a safety requirement, not just a feature.

Consistency

Week by week, one layer at a time. The discipline compounded into a system I can defend end-to-end, not just describe.
